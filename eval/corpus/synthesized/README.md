# Synthesized operator corpus

Recorded 2026-09-26. Three models, Claude Sonnet, Claude Haiku, and Claude Fable, each implemented the 12 tasks of [TASKS.md](TASKS.md) in Numba and in CUDA C++, with no knowledge of OpGate or its gate, and tested each kernel on an RTX A6000. That is 72 kernels in `<model>/<task>/`. On 2026-09-27 a fourth model, Claude Opus, implemented the same tasks in the same way, which adds 24 kernels in `opus/<task>/`, and each model implemented them again in Triton ([TRITON.md](TRITON.md)). The gate's rules were developed on these tasks, the development tasks.

On 2026-09-28, after the gate's last rule change, the same four models implemented the 10 held-out tasks of [HELDOUT.md](HELDOUT.md) in Numba, CUDA C++, and Triton, again with no knowledge of OpGate or its gate, and the unchanged gate decided them. The protocol differs from the first in three ways: the task list fixes each kernel's arguments, so that the three versions agree; each model wrote its Numba and CUDA C++ kernels in one session and its Triton kernels in another at the same time; and every model used the product's environment, numba-cuda 0.30.4 with Numba 0.64 and Triton 3.8.0, whose front ends also wrote the PTX. Two models were reminded once of the task list's layout, with nothing about the gate: Haiku first wrote its Numba and CUDA C++ kernels inside its test files, and Haiku and Sonnet named their Triton arguments with a `_ptr` suffix. Haiku tested 4 of its 10 CUDA C++ kernels; the other 6 only compile. Eight held-out Triton kernels are not in the decision table: Haiku's `min_max`, `days_to_year`, and `merge_sorted`, whose `run` computes the result with PyTorch or Python and never launches the kernel, and Haiku's `run_end_decode` and `sorted_contains` and Sonnet's `run_end_decode`, `sorted_contains`, and `merge_sorted`, which do not compile with the 64-bit scalars that their own `TYPES` state: each starts a search variable at 32 bits, and the 64-bit sizes make it 64-bit in the loop or branch that updates it. Triton's JIT had given the sizes of the models' tests 32 bits. In the first repair round of the held-out tasks, Haiku also wrote four revisions that its prompt did not ask for, of kernels that the gate had accepted or that are not in the table; they were removed, since the loop takes only the revisions a prompt asks for. In the same round, two models' sessions used one scratch path for their tests, and one wrote through the other's symbolic links into two of Opus's CUDA C++ revisions (`sorted_contains`, `valid_rows`); Opus restored both from its tested copies before the round was decided. On 2026-09-29, after the checker froze at commit `0df8e4b`, the same four models implemented the 10 tasks of a second held-out list, [HELDOUT2.md](HELDOUT2.md), committed before they started (`b245bca`), in the protocol of the first: each model wrote its Numba and CUDA C++ kernels in one session and its Triton kernels in another at the same time, from the prompts in `prompts/held-out-2/generation/`, with no knowledge of OpGate or its gate. Every session reported that its kernels passed their tests, with two departures: Haiku tested five of its Triton kernels at sizes up to 100 or 100,000 instead of 1,000,003, and Sonnet's Triton tests of `bloom_build` and `bloom_probe` import a NumPy reference from a scratch file outside the repository. Haiku's Triton `lag` declares `BLOCK_SIZE` as a `tl.constexpr` that its `CONSTANTS` omits, so its arguments are not those of its `signature.json` and it is not in the decision table (`haiku/HELDOUT2_NOTES.md`). A reviewer for each model, a separate session that did not see the gate's decisions, wrote the roles of the new tasks into `<model>/roles.tsv` and the verdict of each kernel, with its evidence, into `<model>/verdicts.tsv`, before the gate decided the kernels. The reviews of Opus's and Sonnet's `coalesce` kernels counted the length of the bitmap `valid` as related to `n`; since `valid`'s length is a size symbol of its own, as for `valid_rows`, those six kernels are `E`, as the other two reviews found for the same code. Buffers with the same length that is not affine, such as `ascii_upper`'s `chars` and `out` of `offsets[n]` bytes each, share one size symbol (`eval/corpus/adapter.py`).

The reports group the corpus into two sets. The development set is the kernels that the gate's rules were built or tuned on: the task sets `development` ([TASKS.md](TASKS.md)), `held-out` ([HELDOUT.md](HELDOUT.md)), `held-out-2` ([HELDOUT2.md](HELDOUT2.md)), and `held-out-3` ([HELDOUT3.md](HELDOUT3.md)), and the DataKernelBench collection. The test set is the task sets `held-out-4` ([HELDOUT4.md](HELDOUT4.md)) and `held-out-5` ([HELDOUT5.md](HELDOUT5.md)), written after a freeze of the checker. The task set names in `eval/corpus/run.py` and in the records stay as they were recorded.

Each task directory has:

- `numba.py`, `numba.ptx`: the Numba kernel and its PTX from Numba 0.65 (built-in CUDA target), NVVM default level, sm_86.
- `kernel.cu`, `kernel.ptx`: the CUDA C++ kernel and its PTX from `nvcc -ptx -arch=sm_86 -O3`, CUDA 13.0.88.
- `test.cu` and a Python test: the models' own tests against NumPy references.
- `signature.json`: the model's statement of each argument. The corpus adapter reads each argument's dtype and length from it.
- `triton.py`, `test_triton.py`: the Triton kernel and the model's test ([TRITON.md](TRITON.md)); `triton.ptx` and `triton.json`, its PTX and the dynamic shared memory of each launch, which Triton states and the PTX does not, and, when the kernel is correct only up to a grid, the grid maxima of the claim (`"grid": [x, y, z]`, decision 33).
- `NOTES.md`: notes the models wrote, where present.
- `repair<k>/`: the model's revision of a kernel that round k - 1 of the repair loop refused (`eval/corpus/repair.py`), with the decisions in [repairs.tsv](repairs.tsv).

`<model>/roles.tsv` is the reviewed table of the argument roles and size symbols of each kernel of the model, which the corpus adapter (`eval/corpus/adapter.py`) reads in place of the models' kinds and `indexes_into`. Each row names a model, a task, an argument, a role, a target, and a minimum, with `-` for a field that the role does not use. The roles are `read`, `write`, and `readwrite` for a buffer; `index-in` and `index-out` for a buffer of indices into the target; `offsets` for a buffer of offsets into the target, whose last offset is the target's length; `size` for a scalar that is the size symbol of the same name; `scalar` for any other scalar; and `symbol` for a size symbol, with its least value as the minimum. The tables differ from the models' statements in 22 arguments: 18 plain outputs that the kernel only writes are `write`, not `readwrite`, and Haiku's `signature.json` omits 4 index roles (`table_rows` of `hash_build`, `out_probe` of `hash_probe`, and `offsets` and `out` of `scatter_by_offsets`). A hash table's capacity has the minimum 1.

Do not put a task directory on `sys.path`: each has a file named `numba.py`, which would shadow the `numba` package, and `triton.py`, which would shadow `triton`.

A kernel enters the decision table only if its arguments are those of its `signature.json`, in the same order, since a binding assigns the PTX parameters by position: `eval/corpus/sources.py` checks the Numba function's parameters, the C prototype, and the Triton function's parameters and `TYPES`. Every Numba and CUDA C++ kernel and the Triton kernels of Opus and Sonnet pass. Each of Haiku's 12 Triton kernels reorders or drops arguments (`NOTES_TRITON.md`), and 9 of them fail Haiku's own tests, so Haiku's Triton kernels are not in the corpus. The Triton kernels of Fable, Haiku, and Sonnet were written a second time, after the first versions were found to carry fixes from the first repair round, which the models had read in their `repair1/` directories; the kept versions were written without access to those directories.

[classification.md](classification.md) classifies every kernel that the initial checker refused (design section 10.3): a defect reachable under the task's contract, a defect reachable when a precondition the catalog cannot check fails, or a limit of the checker, with the features each kernel needs. The harness it names (`run_corpus.py`, `classes_data.py`, the diagnoses under `diag/`) ran a scratch build of that checker and is not kept; the design records the method and the counts.

[e3_triggers.md](e3_triggers.md) runs each of the 27 defect kernels on the input that triggers it, in a pooled layout and with separate allocations, with and without compute-sanitizer (design section 10.5). Its harness and raw results, as they ran, are in `../../records/e3_2026-09-26.tar.gz` (`../../records/e3_2026-09-26.tar.gz`, not included in this archive).

`numba.O1.ptx` and `kernel.O1.ptx` are the same sources compiled at NVVM optimization level 1, the front ends' setting (design section 5.9): Numba 0.65 through the steps of `numba.cuda.compiler.compile` with `nvvm_options={"opt": 1}`, because its public API offers only level 3 or 0; nvcc with `-ptx -arch=sm_86 -O3 -Xcicc -O1`. None of the 72 has a 64-bit division at level 1; 10 have one at level 3. Opus's files come from the product's front ends, numba-cuda 0.30.4 at NVVM level 1 and nvcc with the same flags: `uv run python -m eval.corpus.sources numba opus` and `... nvcc opus` write them. `triton.ptx` is each Triton kernel's PTX from the Triton front end, which `... triton MODEL...` writes.

`classification.md` and `e3_triggers.md` use the level-3 files, `numba.ptx` and `kernel.ptx`.
